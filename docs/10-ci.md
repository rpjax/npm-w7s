# Using w7s in a pipeline

Parts of this tool need no container engine. The parts that do fail loudly rather than
degrading.

## What runs anywhere

```yaml
- uses: actions/checkout@v4
- uses: actions/setup-node@v4
  with:
    node-version: 22
- run: npx @rodrigopjax/w7s gecko validate --json
```

`validate` checks the manifest against the schema and every modification against the pristine
tree. It needs the toolchain image for the pristine comparison, so on a runner without an
engine it validates the schema and the declarations it can check offline and reports the rest
as unchecked — explicitly, in the summary. It never claims to have verified what it could not
reach.

This is the check that belongs on every pull request touching the engine directory.

## What needs a container engine

`make`, `start`, `shell` and `test`. Without an engine they exit
4 naming what is missing; they never produce a partial result.

A cold Gecko build is on the order of two hours and twenty gigabytes of memory, so a hosted
runner is the wrong place for it. The realistic arrangement is a self-hosted runner, or a
scheduled job that produces the package and publishes it as a build artifact.

## Parsing results

Every command accepts `--json` and guarantees one document on stdout.

```bash
w7s gecko validate --json | jq -e '.ok'
w7s gecko status --json | jq -r '.result.artifacts[] | select(.current == false) | .name'
```

| exit code | in a pipeline, usually means                                                   |
| --------- | ------------------------------------------------------------------------------ |
| 2         | the manifest is wrong — fail                                                   |
| 3         | someone committed a working-tree edit that never reached the repository — fail |
| 4         | this runner cannot do this step — skip it, do not retry                        |
| 5         | an artifact is behind; with `--check` this is the currency gate                |
| 6         | a declaration is wrong — read the message                                      |
| 7         | a release-gate test failed                                                     |

## Gating a deploy

The integration point is dockup's `prepare`, so the gate lives in the deploy manifest rather
than in a workflow step:

```jsonc
{ "id": "sidecar", "prepare": ["w7s gecko make sidecar-package"] }
```

A non-zero exit aborts the deploy. See [06-provider.md](06-provider.md).
